# 技术架构设计

## 🖥️ 前端页面规划 (Frontend Pages)

前端基于 React + Tailwind CSS + shadcn/ui 构建，作为 SSO 平台的用户交互入口体系，主要划分为以下几个核心页面模块：

### 1. 认证中心核心页面 (Auth Pages)
*这是用户在各个子系统登录时被重定向到的核心交互区。*
- **`/auth/login` (登录页)**: 用户输入账号密码进行统一登录。需要支持图形验证码防止暴力破解，支持多租户登录入口。
- **`/auth/register` (注册页)**: 新用户注册。
- **`/auth/forgot-password` (忘记密码)**: 邮箱验证码或手机号找回密码流程。
- **`/auth/consent` (OIDC 授权确认页)**: （可选）当第三方子系统请求授权时，展示“应用 X 正在请求获取您的公开信息和邮箱”的确认弹窗/页面。

### 2. 用户个人中心 (User Dashboard)
*普通用户登录 SSO 平台后看到的个人管理面板。*
- **`/dashboard/profile` (个人信息)**: 查看和修改个人基本资料、头像上传等。
- **`/dashboard/security` (安全设置)**: 修改密码、绑定邮箱/手机、查看登录设备和最近的审计日志（异常登录提醒）。
- **`/dashboard/applications` (我的应用)**: 展示该用户当前可以访问或已经授权的子系统应用入口列表（点击后带 Token/Code 跳转子系统）。

### 3. 系统管理后台 (Admin Panel)
*拥有超级管理员角色 (`admin`) 的用户进入的管理控制台。*
- **`/admin/dashboard` (总览看板)**: 展示平台整体运行数据（总用户数、活跃租户、系统应用数、今日请求量等）。
- **`/admin/users` (用户管理)**: 分页展示用户列表，支持按租户、状态、注册时间进行检索；支持禁用/解禁/封号等高权限操作。
- **`/admin/roles` (身份角色管理)**: 管理平台上的宏观角色（如“内部员工”、“外部客户”、“合作商”等），不再处理细粒度权限。
- **`/admin/clients` (OIDC 客户端管理)**: 核心功能！注册接入的子系统，为每个子系统生成并下发 `client_id` 和公钥端点，配置允许的 `redirect_uris`（回调地址）。
- **`/admin/audit-logs` (审计日志)**: 平台安全日志查询，追溯重要敏感操作。

// internal/service/auth_service.go
type AuthService interface {
    // 用户注册

### 2. OIDC模块 (OIDC Module)

#### 核心组件与 JWKS
SSO 的核心不仅在于签发 Token，更在于让接入的各个业务子系统可以**安全地验签**。
必须采用**非对称加密（如 RS256/ES256）**，并在 OIDC 发现层提供 `/.well-known/jwks.json` 端点。

```go
// internal/service/oidc_service.go
type OIDCService interface {
    // 生成授权码
    GenerateAuthorizationCode(req *AuthorizeRequest) (string, error)

    // 验证授权码并生成token
    ExchangeToken(code, clientID, clientSecret string) (*TokenResponse, error)

    // 获取用户信息
    GetUserInfo(accessToken string) (*UserInfo, error)

    // 验证客户端
    ValidateClient(clientID, clientSecret string) (*Client, error)
    
    // 暴露公钥的 JWKS 配置端点供子系统无缝验签
    GetJWKS() ([]byte, error)
}
```

### 3. 身份与角色模块 (Identity & Role Module)

*注：代替了传统业务系统里极其复杂的细粒度 RBAC。SSO 系统应当专注维护使用者的“身份画像”，用户属于哪种宏观 Role 或是 Group，下放具体的 Resource 与 Action 鉴权校验到下游子系统中完成。*

#### 核心组件
```go
// internal/service/identity_service.go
type IdentityService interface {
    // 角色管理
    CreateRole(role *Role) error
    GetRoleByID(id int64) (*Role, error)
    ListRoles() ([]*Role, error)
    UpdateRole(role *Role) error
    DeleteRole(id int64) error

    // 用户身份/角色关联
    AssignRolesToUser(userID int64, roleCodes []string) error
    GetUserRoles(userID int64) ([]*Role, error)
}
```

### 生产级缓存策略（防御缓存击穿与穿透）
使用 `singleflight` 防止大流量瞬间涌入同一失效Key引起的缓存击穿；使用特殊占位符和短 TTL 防御恶意不存在的 ID 查询（缓存穿透）。

```go
import "golang.org/x/sync/singleflight"

type cachedUserRepository struct {
    repo  UserRepository
    cache *redis.Client
    group singleflight.Group
}

func (r *cachedUserRepository) FindByID(ctx context.Context, id int64) (*User, error) {
    key := fmt.Sprintf("user:%d", id)
    
    // 1. 查缓存
    cached, err := r.cache.Get(ctx, key).Result()
    if err == nil {
        if cached == "NULL" { // 防穿透标记
            return nil, gorm.ErrRecordNotFound
        }
        var user User
        json.Unmarshal([]byte(cached), &user)
        return &user, nil
    }

    // 2. 缓存击穿防护 (Singleflight 合并并发请求)
    v, err, _ := r.group.Do(key, func() (interface{}, error) {
        user, err := r.repo.FindByID(ctx, id)
        if err != nil {
            if err == gorm.ErrRecordNotFound {
                // 防穿透：数据库没有，依然缓存占位符，TTL极短 (如 30s)
                r.cache.Set(ctx, key, "NULL", 30*time.Second)
            }
            return nil, err
        }
        // 成功获取数据，回写缓存
        data, _ := json.Marshal(user)
        r.cache.Set(ctx, key, data, 10*time.Minute)
        return user, nil
    })

    if err != nil {
        return nil, err
    }
    return v.(*User), nil
}
```

## 🎯 中间件设计

### 请求拦截与限流
```go
// internal/middleware/rate_limit.go
func RateLimitMiddleware(redis *redis.Client, rate int) gin.HandlerFunc {
    return func(c *gin.Context) {
        key := "rate_limit:" + c.ClientIP()

        count, err := redis.Incr(c, key).Result()
        if err != nil {
            c.Next()
            return
        }

        if count == 1 {
            redis.Expire(c, key, time.Minute)
        }

        if count > int64(rate) {
            c.AbortWithStatusJSON(429, gin.H{"error": "Too many requests"})
            return
        }

        c.Next()
    }
}
```

## 📊 配置管理

### OIDC 与安全配置（非对称加密）
彻底摒弃对称加密 Secret，必须使用 RS256 或 ES256 签名体系保证整体架构中 Token 验签的绝对安全。

```yaml
# configs/config.yaml
server:
  port: 8080
  mode: debug  # debug, release, test

database:
  host: localhost
  port: 3306
  username: root
  password: password
  database: sso_platform
  max_idle_conns: 10
  max_open_conns: 100

redis:
  host: localhost
  port: 6379
  password: ""
  db: 0

jwt:
  # 改为强非对称签名
  algorithm: "RS256"
  private_key_path: "certs/private.pem"
  public_key_path: "certs/public.pem"
  access_token_expire: 3600
  refresh_token_expire: 2592000
  issuer: http://sso.yourdomain.com

oauth:
  authorization_code_expire: 600  # 10分钟

security:
  password_min_length: 8
  max_login_attempts: 5
  lockout_duration: 900  # 15分钟
```

## 📈 性能与架构演进优化

### 数据库层
1. **彻底解耦**: 不再强依赖数据库表级别的外键结构。
2. **读写分离与分表预留**: 业务逻辑与主外键脱钩后，未来做 Sharding 会十分便利。

### 缓存系统
1. **防止雪崩与击穿**: 标准的 `golang.org/x/sync/singleflight` 操作将大大增强平台韧性。
2. **占位符预防穿透**: 有效防止恶意攻击造成的底层 DB 崩溃。

### 接口与认证逻辑
1. **Refresh Token 旋转**: 避免旧长效 Refresh Token 泄露导致的长久驻扎危害。
2. **公有密钥分发**: JWKS 端点支持外部所有挂载本 SSO 的第三方平台无需向研发人员索取敏感 Secret，直接自动化请求端点对 Token 进行验签。
